# Feature implementation matrix

Stage 1 · 13 November 2026 · static baseline, with session product clarification.

## Classification and approval rules

| Class | Meaning in this audit |
| --- | --- |
| A — Implemented | Current source path and relevant wiring exist. Preserve; runtime behavior remains unverified in this audit. |
| B — Partially implemented | A working portion is evidenced, with a specific missing part. |
| C — Deliberately deferred | User confirmed deliberate postponement of unavailable/placeholder candidates during this audit. Existing visual/navigation scaffolding is recorded separately. |
| D — Design-only | Reference UI exists, without functional path or confirmed postponement/approval for that particular design. |
| E — Legacy/obsolete candidate | Possibly superseded; retained pending reference proof and cleanup approval. |
| F — Unconfirmed | Intended behavior, capability or approval is insufficiently established. |

Implementation class, verification, defect and approval are separate dimensions. A source bug can affect A; an intentionally disabled C control is not a broken implementation. No current runtime functionality was executed. AC finding IDs refer to [the audit](PremiumExperienceAudit.md).

**User clarification, this session:** “all of them were deliberately deferred and most of them are ok for inclusion in the complete redesign,” and “the sovenir section is also just a placeholder.” This confirms deferral for the unavailable/placeholder candidates raised: Sound, Accessibility, Tracking/recalibration, Restart, Guide and Souvenir delivery. It supports designing an inclusive complete product but leaves final inclusion of individual candidates reviewable. The user also permits recommending unnecessary items for removal and new needs for discussion. That authorizes recommendations; Stage 1 still prohibits changing assets or implementing them. It does not retroactively approve every Figma-only frame.

Phase codes P1–P11 and D1–D2 are defined in [TransformationRoadmap](TransformationRoadmap.md). P1 safeguards; P2 shell; P3 tokens; P4 glass; P5 motion; P6 core; P7 performers; P8 Settings/privacy/AI; P9 refinement; P10 cleanup; P11 established-feature validation; D1 separately authorized deferred functionality after P10/P11; D2 final all-feature integration. Design specification for retained C features belongs before primary implementation, not in D1.

## Complete design acceptance for every retained deferred feature

Before approving design completeness, each retained C capability must have: (1) named entry and return context, (2) English/Traditional Chinese layout, (3) available/disabled-with-reason/loading/empty/success/error/retry/cancel states as applicable, (4) pointer and keyboard operation plus gesture availability/alternative, (5) focus entry/restoration and topmost dismissal, (6) privacy/cinematic restrictions, (7) motion/reduced-motion behavior, (8) actual service dependency and owner, (9) final inclusion decision and (10) D1 acceptance/rollback plan. F27–F33 define the current candidates; any subsequently identified feature goes through the same review.

No approved future feature should be left as an unexplained blank rectangle, nor exposed as operational before its business logic is authorized. Proposed omissions/merges change the design recommendation only; all working application files remain unchanged in Stage 1.
